# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

**Mikke** (みっけ, the cute Japanese "found it!"): a Telegram reverse image search bot whose persona is a mascot anime girl who finds where pictures come from. Production runs two bots from one process: **@reverseSearch2Bot** (the primary, `BOT_TOKEN`) and **@MikkeSauceBot** (`EXTRA_BOT_TOKENS`), with the same profile. Bot usernames cannot change, and the display name "Mikke" is set once at deploy time (BotFather or `setMyName`), not by the bot at startup. A user sends an image, sticker, GIF or video (or replies `/sauce` to one in a group); the bot looks it up on SauceNAO and answers with the source: title, characters, artist, anime episode and timestamp, plus link buttons. Answers in chats carry a 🎬 "Anime scene" button that runs a trace.moe search on demand. The bot is in many public groups and gets roughly 13k updates a day.

## Running

Python 3.13, uv, aiogram 3, httpx, pydantic-settings, cachetools, sentry-sdk; ruff; pytest with pytest-asyncio and respx. Conventions follow `~/Projects/nHentai` (same author, same stack).

- Local: `cp .env.example .env`, fill in a **test** bot token and the SauceNAO key, then `uv sync` and `uv run mikke`. `BOT_MODE=polling` is the default; it calls `deleteWebhook`, so it must never run with the production token.
- Tests: `uv run pytest`. Offline: Telegram is a `FakeSession` per bot (`tests/conftest.py`) that records every Bot API call but the cached `getMe`, SauceNAO and trace.moe are mocked with respx, and time is an injected `Clock`. Test data and update builders live in `tests/payloads.py`.
- Lint: `uv run ruff check .`. **Never run `ruff format` on the whole project.**
- Docker: `docker build .`; `docker-compose.yml` is the production compose file.

## Configuration

`src/mikke/config.py` `Settings` is the only place that reads the environment (and `.env`, gitignored; `.env.example` is the template, blank values count as unset). Validation errors hide their input, which holds the tokens.

`BOT_TOKEN` (the primary bot), `SAUCENAO_API_KEY` (required); `EXTRA_BOT_TOKENS` (comma-separated tokens of more bots answered by the same process; blank = the primary only; malformed tokens or the same bot twice are rejected); `TRACE_MOE_API_KEY` (optional, a sponsor's key sent as `x-trace-key`; everything works without it); `ADMIN_IDS`, `FAVOURITE_GROUPS` (comma-separated ids); `REPORT_RESULTS`, `REPORT_ERRORS` (default on); `BOT_MODE` (`polling` | `webhook`); `PUBLIC_URL` (base URL of the bots' HTTP server; required for webhook mode); `WEBHOOK_SECRET` (required for webhook mode; the primary bot's, each extra bot's is `derive_secret`: HMAC-SHA256 of the bot id keyed with it); `WEB_HOST`, `WEB_PORT` (default `0.0.0.0:8080`); `LOG_LEVEL`; `SENTRY_DSN`, `SENTRY_ENVIRONMENT`, `SENTRY_TRACES_SAMPLE_RATE`, `SENTRY_RELEASE` (see Sentry).

## Architecture

One process serves every bot: one `Bot` per token (the primary first), one `Dispatcher`, one aiohttp app, one `Searcher` and `SceneSearcher` (caches, SauceNAO and trace.moe limits and lock), one flood protection. aiogram hands each handler the bot that received the update (`bot` argument, and the bound `message.answer`, `callback.answer`, ...); nothing may use the primary bot where the receiving one is meant, because a file_id only works with the bot that received the file. `file_unique_id`, the cache key, is the same for every bot.

Package `src/mikke/`:

- `__main__.py` — loads `Settings`, sets up logging through `RedactingFormatter` (`Settings.secrets()`: every bot token, the SauceNAO key, the trace.moe key, the webhook secret and the derived ones never reach the logs, tracebacks included), starts Sentry inside the event loop, wires everything, starts the HTTP server in both modes, asks every bot for `getMe` (cached from then on), then either registers every bot's webhook (`setWebhook(<PUBLIC_URL><path>, secret_token, allowed_updates)`, see `web.webhooks`) and waits for SIGTERM, or `deleteWebhook` for every bot + long polling of all of them. On SIGTERM in webhook mode it stops the listener and gives running updates up to 8 s (`InFlight`) before closing.
- `bot.py` — `build_bot(token)` (HTML parse mode, link previews off), `build_dispatcher` (one for all bots; DI: `searcher`, `scenes`, `reporter`, `in_flight`; error handler; `observability.tag_bot` on updates and on the error handler, which aiogram runs outside the update middlewares) and `InFlight`, an outer update middleware that counts updates in progress, because aiogram does not wait for its background webhook tasks.
- `handlers.py` — one `main` router (`/start`, `/help`, added to a group, inline query, chosen inline result) with a nested `search` router for everything that starts a search: the group trigger (`/sauce`, `/source`, `sauce`, `source`, `what?` in reply to media; commands without media get the usage hint), private media, photos in `FAVOURITE_GROUPS`, and presses of the 🎬 button (callback data `scene`). Flow: reply with the 🔍 "Mikke is looking..." placeholder, `Searcher`, edit the placeholder (or the inline message). File searches in chats get a last keyboard row with the 🎬 button on every answer except "invalid file" (`Answer.invalid_file`); inline answers never do. `_edit` must not leave the placeholder spinning: on a 400 it retries without the link buttons (the 🎬 row stays), on flood control it waits and retries once. A 🎬 press takes the media from `callback.message.reply_to_message` (the answer always replies to it), runs `SceneSearcher`, and sends a new reply to that media; limits, errors and a missing media are a popup alert on the button instead. The callback is answered after the search, so a late answer ("query is too old") is only logged. `on_error` (aiogram's error handler) logs expected errors (`observability.is_expected`) as a warning and stops there; anything else is logged at ERROR, which becomes the Sentry event, and reported to the owner.
- `flood.py` — `FloodMiddleware`, an inner middleware on the `search` router, so only updates that would start a search count: more than 20 messages within 3 seconds per user (to any of the bots) are dropped, and more than 5 🎬 presses within 60 seconds (a separate instance, since trace.moe's quota is small). Time is the message date, so a backlog replayed after downtime is not a flood; presses have no date and use the clock.
- `media.py` — `find_media` (largest photo; static sticker, or the thumbnail of animated/video stickers, GIFs and videos; image documents by extension) and `normalize_url` for inline queries.
- `search.py` — `Searcher`: 24h `TTLCache` of accepted matches (200 entries, keyed by `file_unique_id` or `url:<url>`, empty list = cached "no result"; errors and limits are not cached; shared by all bots), quota check before downloading, `getFile` + download through the receiving bot, SauceNAO, answer, owner report. `image_url(bot, file_id)` is `<PUBLIC_URL>/img/<bot id>/<file_id>`, built per answer, so a cached "no result" still links the asking bot's file. Always returns an `Answer`; unexpected exceptions become the error text plus an error report. `download()` (shared with `SceneSearcher`) re-raises download failures as `DownloadError` without the aiohttp original, whose text quotes the file URL.
- `saucenao.py` — `SauceNao` client. Uploads bytes (multipart `file`) or passes a public URL (inline mode); never a Telegram file URL. Tracks `short_remaining`/`long_remaining` from the JSON header: short window exhausted blocks for 30 s, the daily one for 10 min (it is rolling, so it gets probed again), HTTP 429 likewise (daily if the message says so). The headers only describe finished requests, so it also counts its own sends and allows at most `short_limit` (4) per 30 s. While blocked, `QuotaExceededError` is raised without an HTTP call.
- `tracemoe.py` — `TraceMoe` client for `POST https://api.trace.moe/search?anilistInfo&cutBorders` with the image bytes (multipart `image`), `x-trace-key` when a key is set. An `asyncio.Lock` keeps it to one search at a time, because a guest has concurrency 1 and a second parallel search fails with HTTP 402 "Concurrency limit exceeded". HTTP 402 "Search quota depleted" blocks it for 10 min (`QuotaExceededError` without an HTTP call, also for searches already waiting on the lock); every other failure is `TraceMoeError`.
- `scenes.py` — `SceneSearcher`: own 24h `TTLCache` (200 entries) of the best trace.moe result per `file_unique_id` (empty list = cached "not found"; errors and limits are not cached), quota check before downloading, `download()`, trace.moe; returns an `Answer` or an `Alert`. Errors are reported to the owner. `render` (pure): English title, romaji below it when different (AniList info; bare id → file name), episode (`episode_start`/`episode_end`, else the file-name `episode`), `from`-`to` as mm:ss (h:mm:ss past an hour), similarity, the weak-match line below 90% (trace.moe's own threshold), AniList and MyAnimeList (`idMal`) buttons.
- `results.py` — pure functions: `select` (similarity >= 60, within 7 of the best), `render_text`, `links` (one per site, `Source`, MAL search for AniDB without a MAL link, max 6, first is "View on X"; only URLs Telegram accepts as buttons, since booru `source` fields are free text), `grid` (two per row, last row up to three), `keyboard` (None when empty), `fallback_keyboard` (two rows of three, see `ENGINES`; every template takes the percent-encoded `<PUBLIC_URL>/img/<bot id>/<file_id>`):
  - Google Lens `https://lens.google.com/uploadbyurl?url={}`
  - Yandex `https://yandex.com/images/search?rpt=imageview&url={}`
  - Bing `https://www.bing.com/images/search?view=detailv2&iss=sbi&form=SBIVSP&sbisrc=UrlPaste&q=imgurl:{}`
  - SauceNAO `https://saucenao.com/search.php?url={}`
  - ascii2d `https://ascii2d.net/search/url/{}?type=color` (what ascii2d's official browser extension opens)
  - TinEye `https://tineye.com/search?url={}`

  Checked against the live sites on 2026-09-27 with a public anime screenshot: Lens, Yandex and Bing returned results for it, TinEye served its search page. SauceNAO and ascii2d show a Cloudflare check first (ascii2d an interactive "Verify you are human" box), which people pass in a browser but scripts do not.
- `reports.py` — `Reporter`: to every `ADMIN_IDS` user, through the bot that handled the update (its file_ids only work there), found results (SauceNAO link to the public image URL + text + buttons, then the original media resent by file_id with the matching send method, because Telegram cannot resend thumbnails) and errors (with the bot token replaced). An admin who never started a bot makes its reports fail with Forbidden: logged as a WARNING once per bot and admin (not a Sentry event), the rest are skipped silently.
- `web.py` — the single aiohttp app: a webhook per bot (aiogram `SimpleRequestHandler`, webhook mode only, `X-Telegram-Bot-Api-Secret-Token` checked, 401 otherwise; `webhooks()`: the primary bot on `POST /` with `WEBHOOK_SECRET`, where its webhook has always been, each extra bot on `POST /<bot id>/` with its derived secret; no path holds a token), `GET /img/<bot id>/<file_id>` (through that bot, 404 for an unknown one; validates the id, `getFile` on every request, streams images only, `HEAD` without downloading, 404/502 otherwise), `GET /img/<file_id>` (the same through the primary bot, for links sent before there were several bots), `GET /healthz`.
- `observability.py` — `init_sentry`, `is_expected`, `Scrubber`, `tag_bot`; see Sentry.
- `texts.py` — user-facing strings.

## Sentry

Org `nicosmile`, project `mikke-bot`, team `telegram-bots`, US region (https://nicosmile.sentry.io/projects/mikke-bot/). `SENTRY_DSN` turns it on (blank or unset: the SDK is never initialised, so tests and local runs send nothing); `SENTRY_ENVIRONMENT` (default `production`, `development` for local runs); `SENTRY_TRACES_SAMPLE_RATE` (default 0.0, errors only). The release is `SENTRY_RELEASE`: the Dockerfile's `SENTRY_RELEASE` build arg, which CI sets to `mikke-bot@<commit sha>`; without it there is no release (the SDK's `git rev-parse HEAD` guess is switched off).

- Events carry the tag `bot`, the username of the bot that received the update (`tag_bot`, an outer middleware that forks the scope) or of the `/img/` link's bot (the request's scope).
- Reported, once each: handler errors (aiogram's error handler swallows them, so `on_error`'s `logger.error` is the event, through the logging integration; there is no aiogram integration), exceptions in the aiohttp routes `/img/` and the webhook (aiohttp integration, which ignores aiohttp's own error log), and every other ERROR log, like `logger.exception` in the searchers (SauceNAO or trace.moe failing, download failures). INFO and above are breadcrumbs.
- Not reported: SauceNAO and trace.moe quotas (`QuotaExceededError`), no result, flood protection, Telegram's "message is not modified", a message deleted before the answer, a user who blocked the bot, an admin who never started it, or a chat that took away its right to write (`is_expected`, also enforced in `before_send`), `/img/` 404 and 502 (`failed_request_status_codes=set()`). They stay INFO/WARNING logs.
- Scrubbing: `before_send`, `before_send_transaction` and `before_breadcrumb` replace `Settings.secrets()` (every bot token and webhook secret among them, also percent-encoded) and any `/bot<id>:<token>` or `api_key=` value in every string with `[Filtered]`; the `EventScrubber` denylist adds `X-Telegram-Bot-Api-Secret-Token` and `x-trace-key`; `request.env` (REMOTE_ADDR) is dropped. No Telegram user data beyond numeric ids: `include_local_variables=False` (locals hold messages and token URLs), `max_request_body_size="never"` (webhook bodies are whole updates), `send_default_pii=False`, and `on_error` sets only the user id, the update type and the chat id. `trace_propagation_targets=[]` keeps tracing headers away from Telegram, SauceNAO and trace.moe.
- Tests (`tests/test_observability.py`) start the SDK with a recording `Transport`, so nothing leaves the machine.

## Things to watch

- The bot tokens must never leave the process: SauceNAO and trace.moe get bytes, fallback and report links use `<PUBLIC_URL>/img/<bot id>/<file_id>`, webhook paths use the bot id. aiohttp errors from Telegram file downloads quote the file URL, token included, so never log or report them raw (`DownloadError`, the `/img/` warning, `Reporter.error`, `RedactingFormatter`). httpx logging is set to WARNING because it logs request URLs, and the SauceNAO `api_key` is in the query string.
- `/img/` calls `getFile` per request on purpose: file_ids stay valid, `file_path` links expire after about an hour, and fallback links sit in old messages. That is also why `/img/<file_id>`, without a bot id, must keep working through the primary bot.
- Inline results carry the 🔍 keyboard on purpose: without a keyboard Telegram sends no `inline_message_id` to edit. `chosen_inline_result` needs inline feedback enabled in @BotFather (`/setinlinefeedback`), for each bot.
- Group keywords (`sauce` without a slash) and favourite-group photos only reach a bot with its privacy mode off (set per bot in @BotFather).
- trace.moe never runs automatically. A guest gets 100 searches per IP (the API docs and server code count a rolling 24 hours; `GET https://api.trace.moe/me` shows quota and usage, and anything else on the server calling trace.moe uses the same quota) and concurrency 1; failed searches (4xx/5xx) do not count. Keep it behind the button, and keep the lock and the cache.
- Deliberately dropped from production: Amplitude analytics, proxy rotation, TinEye scraping, `webpToPng.php`, pm2, the storebot rating text, the TinEye `sn|` callback buttons, the `/privacy` command.

## Production

- Server `skrime-vps` (SSH alias), compose project `~/BOTS/mikke/` (`docker-compose.yml` = the one in this repo, `.env` 600, `deploy.sh`), service and container `mikke` in the external Docker network `bots-network`, internal port 8080, image `ghcr.io/nyasume/mikke-bot:latest`.
- Traefik behind Cloudflare, `~/traefik/config/mikke.yml`: `https://anybyte.org/telebot/mikke` → `mikke:8080` with the `/telebot/mikke` prefix stripped, so the bot sees `/`. `PUBLIC_URL=https://anybyte.org/telebot/mikke`: @reverseSearch2Bot's webhook is `https://anybyte.org/telebot/mikke/`, @MikkeSauceBot's `https://anybyte.org/telebot/mikke/<its bot id>/`, and images are `https://anybyte.org/telebot/mikke/img/<bot id>/<file_id>` (links sent before, `.../img/<file_id>`, keep working) over the same route. Every bot registers its webhook itself on start: the primary with `WEBHOOK_SECRET`, the others with the secret derived from it.
- The server's `.env` has `BOT_TOKEN` (@reverseSearch2Bot) and `EXTRA_BOT_TOKENS` (@MikkeSauceBot). An admin gets reports from @MikkeSauceBot only after pressing Start in it; until then its reports are dropped with one warning in the log.
- CI/CD, `.github/workflows/ci.yml`: ruff and pytest on every push and PR; pushes to `main` build and push `ghcr.io/nyasume/mikke-bot` (`latest` + `sha-<short>`); deploy only when the workflow is run by hand (Actions → CI → Run workflow, `deploy` checked), mirroring the manual deploy of the GitLab bots. The deploy job SSHes with a key that `~/.ssh/authorized_keys` pins to `restrict,command="/home/anybyte/BOTS/mikke/deploy.sh"`, so it can only pull and restart the bot; the job's `GITHUB_TOKEN` goes over stdin for the GHCR pull, into a throwaway `DOCKER_CONFIG` deleted on exit. Repo secrets: `SSH_PRIVATE_KEY`, `SSH_KNOWN_HOSTS`, `SSH_HOST`, `SSH_USER`. `deploy.sh` and the server's compose file are not deployed by CI; change them on the server by hand.
- Bot profile (display name "Mikke", descriptions, commands), the same for both bots, is set through the Bot API (`setMyName`, `setMyDescription`, `setMyShortDescription`, `setMyCommands`); the avatar through BotFather `/setuserpic`. @reverseSearch2Bot is owned by the user's second Telegram account.
- The old Node.js bot (`~/BOTS/reverseSearchBot/`, container `rsbot`, Traefik `/telebot/rsbot` and `/rsbotphp`, the php container and the nginx `:6004` block) was replaced by Mikke on 2026-09-27.
- Secrets (bot tokens, SauceNAO key, admin ids, webhook secret, trace.moe key, Sentry DSN) never go into git.
- The server's `.env` has `SENTRY_DSN` and must not set `SENTRY_RELEASE`: a line there, even a blank one, overrides the release baked into the image.
- Do not touch the server or the production bots, and do not call Telegram with the production tokens, unless the user asks.
