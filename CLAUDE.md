# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

**Mikke** (みっけ, the cute Japanese "found it!"): a Telegram reverse image search bot whose persona is a mascot anime girl who finds where pictures come from. Production runs two bots from one process: **@reverseSearch2Bot** (the primary, `BOT_TOKEN`) and **@MikkeSauceBot** (`EXTRA_BOT_TOKENS`), with the same profile. Bot usernames cannot change, and the display name "Mikke" is set once at deploy time (BotFather or `setMyName`), not by the bot at startup. A user sends an image, sticker, GIF or video (or replies `/sauce` to one in a group); the bot looks it up on SauceNAO and answers with the source: title, characters, artist, anime episode and timestamp, plus link buttons. Answers in chats carry a 🎬 "Anime scene" button that runs a trace.moe search on demand. Users can add their own free SauceNAO key (`/apikey`, or just the key in a private chat), which their searches then use instead of the shared one. The bot is in many public groups and gets roughly 13k updates a day.

History:

It was imported rather than forked because the Python rewrite shares no code with it. The Node.js code was deleted once the rewrite covered it; `git show b171949` has it.
- Production still runs an older fork of that code, [AnyByte/reverseSearchBot](https://github.com/AnyByte/reverseSearchBot) (2020, Telegraf 3, webhook mode). On 2026-09-27 it was revived after four months offline with local patches: SauceNAO JSON API instead of HTML scraping (now behind a Cloudflare challenge), dead SOCKS proxies removed, Node 22. Those patches are not in any git history; the result formatter they introduced is kept for reference in `docs/legacy/deployed-parseSauceNao.js`.

- Before the first deployment the rewrite was renamed to Mikke: repo `reverse-search-bot` → `mikke-bot`, package `reverse_search_bot` → `mikke`, console script and container `rsbot` → `mikke`.

Single admin and sole developer: the user.

## Running

Python 3.13, uv, aiogram 3, httpx, pydantic-settings, cachetools, sentry-sdk; ruff; pytest with pytest-asyncio and respx. Conventions follow `~/Projects/nHentai` (same author, same stack).

- Local: `cp .env.example .env`, fill in a **test** bot token and the SauceNAO key, then `uv sync` and `uv run mikke`. `BOT_MODE=polling` is the default; it calls `deleteWebhook`, so it must never run with the production token.
- Tests: `uv run pytest`. Offline: Telegram is a `FakeSession` per bot (`tests/conftest.py`) that records every Bot API call but the cached `getMe`, SauceNAO and trace.moe are mocked with respx, and time is an injected `Clock`. Test data and update builders live in `tests/payloads.py`.
- Lint: `uv run ruff check .`. **Never run `ruff format` on the whole project.**
- Docker: `docker build .`; `docker-compose.yml` is the production compose file.

## Configuration

`src/mikke/config.py` `Settings` is the only place that reads the environment (and `.env`, gitignored; `.env.example` is the template, blank values count as unset). Validation errors hide their input, which holds the tokens.

`BOT_TOKEN` (the primary bot), `SAUCENAO_API_KEY` (required, the shared key); `EXTRA_BOT_TOKENS` (comma-separated tokens of more bots answered by the same process; blank = the primary only; malformed tokens or the same bot twice are rejected); `TRACE_MOE_API_KEY` (optional, a sponsor's key sent as `x-trace-key`; everything works without it); `ADMIN_IDS`, `FAVOURITE_GROUPS` (comma-separated ids); `REPORT_RESULTS` (an activity report for every search, found or not, and the key events), `REPORT_ERRORS` (handler failures, and failed searches when `REPORT_RESULTS` is off; both default on); `BOT_MODE` (`polling` | `webhook`); `PUBLIC_URL` (base URL of the bots' HTTP server; required for webhook mode); `WEBHOOK_SECRET` (required for webhook mode; the primary bot's, each extra bot's is `derive_secret`: HMAC-SHA256 of the bot id keyed with it); `WEB_HOST`, `WEB_PORT` (default `0.0.0.0:8080`); `DATA_DIR` (where `mikke.sqlite3`, the users' keys, lives; default `./data`, `/data` in the image and set again in `docker-compose.yml`); `LOG_LEVEL`; `SENTRY_DSN`, `SENTRY_ENVIRONMENT`, `SENTRY_TRACES_SAMPLE_RATE`, `SENTRY_RELEASE` (see Sentry).

## Architecture

One process serves every bot: one `Bot` per token (the primary first), one `Dispatcher`, one aiohttp app, one `Searcher` and `SceneSearcher` (caches, SauceNAO and trace.moe limits and lock), one `KeyStore` (users' SauceNAO keys by Telegram user id), one flood protection. aiogram hands each handler the bot that received the update (`bot` argument, and the bound `message.answer`, `callback.answer`, ...); nothing may use the primary bot where the receiving one is meant, because a file_id only works with the bot that received the file. `file_unique_id`, the cache key, is the same for every bot.

Package `src/mikke/`:

- `__main__.py` — loads `Settings`, sets up logging through `RedactingFormatter` (`Settings.secrets()`: every bot token, the SauceNAO key, the trace.moe key, the webhook secret and the derived ones never reach the logs, tracebacks included), starts Sentry inside the event loop, wires everything, starts the HTTP server in both modes, asks every bot for `getMe` (cached from then on), then either registers every bot's webhook (`setWebhook(<PUBLIC_URL><path>, secret_token, allowed_updates)`, see `web.webhooks`) and waits for SIGTERM, or `deleteWebhook` for every bot + long polling of all of them. On SIGTERM in webhook mode the webhooks answer 503 from then on, so Telegram keeps those updates and redelivers them after its backoff to the next container (`setWebhook` keeps pending updates: updates sent during a deploy arrive a little late); it stops the listener and gives running updates up to 8 s (`InFlight`) before closing.
- `bot.py` — `build_bot(token)` (HTML parse mode, link previews off), `build_dispatcher` (one for all bots; DI: `searcher`, `scenes`, `reporter`, `keys`, `in_flight`; error handler; `observability.tag_bot` on updates and on the error handler, which aiogram runs outside the update middlewares) and `InFlight`, the outermost update middleware (around aiogram's own, so an update counts until its error has been reported), that counts updates in progress, because aiogram does not wait for its background webhook tasks; a webhook request counts from its arrival until its update's task has started (`web.counted`), and `closing` (set on SIGTERM) refuses webhooks.
- `handlers.py` — one `main` router (`/start`, `/help`, added to a group, inline query, the 🔍 placeholder button, the nested `apikey` router) with a nested `search` router for everything that starts a search: the group trigger (`/sauce`, `/source`, `sauce`, `source`, `what?` in reply to media; commands without media get the usage hint), private media, photos in `FAVOURITE_GROUPS`, presses of the 🎬 button (callback data `scene`) and chosen inline results. Flow: reply with the 🔍 "Mikke is looking..." placeholder (a press on its 🔍, callback `noop`, is only answered), `Searcher`, edit the placeholder (or the inline message), then `Reporter.search` (the one who asked is the sender of `/sauce`, not of the media). The `Asker` handed to the `Searcher` picks the key: the sender of a private media message, of `/sauce` (not of the media) or of the inline query; none (the shared key) for favourite-group photos, channels and anonymous admins. File searches in chats get a last keyboard row with the 🎬 button on every answer except "invalid file" (`Answer.invalid_file`); inline answers never do. `_edit` must not leave the placeholder spinning: on a 400 it retries without the link buttons (the 🎬 row stays), except for the expected ones (not modified, message gone), which the links are not to blame for, on flood control it waits as long as Telegram asks and retries once, and after a network or server error it retries once (each at most once; an edit that went through anyway comes back "not modified"). A 🎬 press takes the media from `callback.message.reply_to_message` (the answer always replies to it), runs `SceneSearcher`, and sends a new reply to that media; limits, errors and a missing media are a popup alert on the button instead. The callback is answered after the search, so a late answer ("query is too old") is only logged; the report comes after that (a press without the media is no search and gets none). `on_error` (aiogram's error handler) logs expected errors (`observability.is_expected`) as a warning and stops there; anything else is logged at ERROR, which becomes the Sentry event, and reported to the owner.
- `apikey.py` — the `apikey` router, users' own SauceNAO keys. In private: `/apikey` (and the 🔑 "Add my free key" button, callback `key:add`) sends the numbered steps with a URL button to https://saucenao.com/user.php?page=search-api and the saved key's status (tail only, `…a1b2`); `/apikey <key>`, or a message that is nothing but 40 lowercase hex characters (the shape SauceNAO hands out; anything else, pictures included, is not a key), checks the key with one real search (`SauceNao.account()`), then saves it and answers with the account type, limits and searches left today; a key SauceNAO rejects is not saved, and a check that fails saves nothing and answers `KEY_CHECK_FAILED` (logged at ERROR, or as a WARNING when SauceNAO is down). `/apikey remove` and the 🗑 button (`key:remove`) forget it. `/apikey <anything>` in a group is never saved: the message is deleted if the bot may, and the warning is not a reply, which would quote the key; `/apikey` alone there points to the private chat. Key events (added, removed, refused) go to `Reporter.key`. Checks (`/apikey <key>` and bare keys in private, a nested router) are flood limited to 5 per 60 s per user; the steps, the removal and the cleanup of a key sent in a group never are. Key changes are one at a time per user (`CHANGES`, a `KeyLocks`), so a removal sent while a key is being checked comes after it.
- `keys.py` — `KeyStore`: SQLite `DATA_DIR/mikke.sqlite3`, table `saucenao_keys(user_id, api_key, valid)`, every call in `asyncio.to_thread` on a connection of its own; the file is made 0600, also one made before, and the directory 0700 when it creates it (an existing `DATA_DIR` is left as it is). `invalidate(user_id, key)` marks a rejected key once (it returns True for one caller only, and leaves a key the user replaced since), so the user is told once. `UserKey.masked` and its `repr` show only the tail.
- `flood.py` — `FloodMiddleware`, an inner middleware on the `search` router, so only updates that would start a search count: more than 20 messages within 3 seconds per user (to any of the bots) are dropped, more than 5 🎬 presses within 60 seconds (a separate instance, since trace.moe's quota is small), and more than 20 chosen inline results within 3 seconds (its own instance; a dropped one stays on "Mikke is looking..."); the key checks of the `apikey` router have their own instance (5 per 60 s). Time is the message date, so a backlog replayed after downtime is not a flood, and each update drops only the stamps too old for its own window and counts the ones around it, so a backlog handled after a newer update is neither taken for a flood nor lets one through; presses and inline results have no date and use the clock. A dropped 🎬 press is still answered (silently), so its button stops spinning.
- `media.py` — `find_media` (largest photo; static sticker, or the thumbnail of animated/video stickers, GIFs and videos; image documents by extension, GIF files included) and `normalize_url` for inline queries.
- `search.py` — `Searcher`: 24h `TTLCache` of accepted matches (200 entries, keyed by `file_unique_id` or `url:<url>`, empty list = cached "no result"; errors and limits are not cached; shared by all bots and keys; searches of the same image run one at a time (`KeyLocks`), so one that waited finds the answer cached, or, after a failure, searches with its own asker's key), then the asker's key from the `KeyStore`, `getFile` + download through the receiving bot once the search has its SauceNAO slot, SauceNAO, answer. Whose key: the asker's valid key (`Outcome.key` "own"); when it is used up for the day ("used_up") or SauceNAO rejects it ("rejected": marked invalid, `KEY_REJECTED` appended to that one answer) the shared key searches instead, with the file downloaded once; an own key's 30-second line that is too long ends as "limit" without touching the shared one. `saucenao(key)` is the client for a user's key (an `LRUCache` of 1000, each with its own limits; the shared key's client is separate). In private, a limit for someone without a usable key appends `KEY_PITCH` and a 🔑 "Add my free key" row (`ADD_KEY_CALLBACK`); groups, inline and automatic searches get the short `LIMIT_REACHED`. The cache holds `(similarity, data)` pairs. `image_url(bot, file_id)` is `<PUBLIC_URL>/img/<bot id>/<file_id>`, built per answer, so a cached "no result" still links the asking bot's file. Always returns an `Answer`, whose `Outcome` (`reports.py`: status, cached, the matches as `Hit`s, the error text, the `Quota`) is for the owner report; the quota is the `usage` of the key that searched last, read right after its call, so a search gets the numbers SauceNAO sent with its own answer ("own key" only when the user's key answered; a limit or an error gets what is known), and a cache hit gets the shared key's last known ones; exceptions become the error text. SauceNAO down (`saucenao.UnavailableError`, with the user's key too: the shared one would meet the same outage) answers `SAUCENAO_DOWN` ("try another engine or again in a minute") with the fallback buttons and logs a WARNING; any other exception answers `ERROR` and logs "Search failed" at ERROR, the Sentry event. A result is rendered before it is cached, so one that cannot be shown is an error answer, not a cached failure. It sends no reports itself. `download()` (shared with `SceneSearcher`) re-raises download failures as `DownloadError` without the aiohttp original, whose text quotes the file URL.
- `saucenao.py` — `SauceNao` client for one API key (`with_key` makes another over the same httpx client). Uploads bytes (multipart `file`, from an `upload` callable run only once the search has its slot) or passes a public URL (inline mode, key checks); never a Telegram file URL. The 30-second window is a line, not a refusal (a waiting search looks again every second, so a slot given back by a failed download is used at once): a search waits in arrival order (an `asyncio.Lock`) for a free slot, counting its own sends (the headers only describe finished requests, so at most `short_limit`, 4, per 30 s) and pausing 30 s after `short_remaining` 0 or a short HTTP 429, which also puts that search back in line. A search whose turn is expected more than `MAX_WAIT_SECONDS` (60) away raises `QuotaExceededError` at once; one let in gives up only if it is pushed back by more than another window. The daily window (`long_remaining` 0, or a 429 saying "daily") rests the key for 10 min (it is rolling, so it gets probed again): `QuotaExceededError(daily=True)` without an HTTP call, also for searches already in line. HTTP 403 with JSON is `InvalidKeyError` (a made-up key gets `{"header":{"status":-1,"message":"The anonymous account type does not permit API usage."}}`, checked live on 2026-09-28; Cloudflare's 403 page is HTML and stays a `SauceNaoError`, not retried), and rests the key for 10 min. Error texts are the status and SauceNAO's own JSON `message`, never the body, which Cloudflare makes a whole HTML page: `HTTP 403`, `HTTP 200: not JSON`, and for its 52x codes Cloudflare's meaning (`outages.py`). SauceNAO down (a 5xx, 52x included) or out of reach (a timeout, a connection error) is retried once, 3 s later, if the retry can go out before the search's deadline (`MAX_WAIT_SECONDS` from its start; so a 60 s read timeout never is), and only if the key was not used up or rejected meanwhile; the retry takes the failed request's slot instead of another one (a request Cloudflare could not pass on cost nothing; one that did cost a search, and SauceNAO's 429 corrects the count). Down after that is `UnavailableError` (a `SauceNaoError`), e.g. `HTTP 521 (Cloudflare: web server is down)`; the retry itself is a WARNING log. `usage` is (used, limit) of the daily window from the latest JSON header (`long_limit` - `long_remaining`, 429s included), for the owner reports; a daily limit makes it used up even when that answer has no numbers; None before the key's first answer. `account()` checks a key with a search of SauceNAO's own banner by URL and returns `Account` (type: 1 Basic (free), 2 Premium; limits; searches left). Error texts and logged SauceNAO messages never contain the key (`_hide`). The `sleep` is injected, so tests run the line on a fake clock.
- `tracemoe.py` — `TraceMoe` client for `POST https://api.trace.moe/search?anilistInfo&cutBorders` with the image bytes (multipart `image`), `x-trace-key` when a key is set. An `asyncio.Lock` keeps it to one search at a time, because a guest has concurrency 1 and a second parallel search fails with HTTP 402 "Concurrency limit exceeded"; the image comes from an `upload` callable run only once the search has its turn, so searches in line hold no image (the Telegram download happens inside the lock). HTTP 402 "Search quota depleted" blocks it for 10 min (`QuotaExceededError` without an HTTP call, also for searches already waiting on the lock); every other failure is `TraceMoeError`, whose text is the status and trace.moe's own `error`, never the body. trace.moe down (a 5xx) or out of reach (a connection error or connect timeout) is retried once, 3 s later, inside the lock with the same image, so the search keeps its turn; a read, write or pool timeout is not (`outages.SLOW`: it took the whole minute, with the other presses waiting). Down after that is `UnavailableError` (a `TraceMoeError`); failed searches cost no quota. Results and "Search quota depleted" carry `quota` and `quotaUsed` (checked live on 2026-09-28 and in trace.moe's `src/search.ts`, where `quotaUsed` is counted before the search, which is logged after it answers; with `cutBorders` a search costs 1), so `usage`, (used, limit) for the owner reports, is `quotaUsed` + 1 after a result and `quotaUsed` after a depleted quota, with no call to `GET /me`; `sponsored` says whether a key is set.
- `scenes.py` — `SceneSearcher`: own 24h `TTLCache` (200 entries) of the best trace.moe result per `file_unique_id` (empty list = cached "not found"; errors and limits are not cached; presses on the same image run one at a time, `KeyLocks`), quota check, then trace.moe, which runs `download()` once the search has its turn; returns an `Answer` or an `Alert` (`SCENE_ERROR` for any failure: logged as a WARNING when trace.moe is down, `UnavailableError`, otherwise at ERROR), both with the `Outcome` for the owner report, whose `Quota` is `TraceMoe.usage` read right after the search (a cache hit or a blocked quota gets the last known one), as "guest" or "sponsor key"; a scene is rendered before it is cached. `render` (pure): English title, romaji below it when different (AniList info; bare id → file name), episode (`episode_start`/`episode_end`, else the file-name `episode`), `from`-`to` as mm:ss (h:mm:ss past an hour), similarity, the weak-match line below 90% (trace.moe's own threshold), AniList and MyAnimeList (`idMal`) buttons; `hit` is the same scene for the report.
- `results.py` — pure functions: `select` (`(similarity, data)` pairs: similarity >= 60, within 7 of the best), `hits` (each match with its similarity and its own links, for the report), `render_text`, `links` (one per site, `Source`, MAL search for AniDB without a MAL link, max 6, first is "View on X"; only URLs Telegram accepts as buttons, since booru `source` fields are free text), `grid` (two per row, last row up to three), `keyboard` (None when empty), `fallback_keyboard` (two rows of three, see `ENGINES`; every template takes the percent-encoded `<PUBLIC_URL>/img/<bot id>/<file_id>`):
  - Google Lens `https://lens.google.com/uploadbyurl?url={}`
  - Yandex `https://yandex.com/images/search?rpt=imageview&url={}`
  - Bing `https://www.bing.com/images/search?view=detailv2&iss=sbi&form=SBIVSP&sbisrc=UrlPaste&q=imgurl:{}`
  - SauceNAO `https://saucenao.com/search.php?url={}`
  - ascii2d `https://ascii2d.net/search/url/{}?type=color` (what ascii2d's official browser extension opens)
  - TinEye `https://tineye.com/search?url={}`

  Checked against the live sites on 2026-09-27 with a public anime screenshot: Lens, Yandex and Bing returned results for it, TinEye served its search page. SauceNAO and ascii2d show a Cloudflare check first (ascii2d an interactive "Verify you are human" box), which people pass in a browser but scripts do not.
- `reports.py` — `Reporter`, to every `ADMIN_IDS` user through the bot that handled the update (its file_ids only work there). `search()` is the activity report, one per search (SauceNAO in chats and inline, trace.moe behind 🎬), which the handlers send once the user has the answer; it never raises. It is a silent `sendRichMessage` (Bot API 10.1, aiogram's own `SendRichMessage`) in rich HTML: the searched image embedded as `<img src="tg://photo?id=searched"/>` (a photo by its file_id; stickers, image files and the thumbnails searched for GIFs, videos and animated stickers by their `/img/` link, which Telegram fetches from us; the inline URL as it is), the outcome (found: the answer as the user saw it, then each match with its similarity and links; nothing found; quota used up; error with the exception text; Telegram would not give the file, with its reason), who asked (a `tg://user?id=` mention, @username, id; the sender chat for channels and anonymous admins), where (private chat; the group title with its public link, its id and a link to the searched message, public or `t.me/c/`; inline mode with the URL), the quota (`Outcome.quota`, a `Quota`: `📊 SauceNAO: 57/100 used (24 h) · shared key`, or `· own key`, or `📊 trace.moe: 12/100 used (24 h) · guest`, or `· sponsor key`; never a key; left out while the engine has not reported it since the start), the bot, "💾 from the cache", "🔑 own key" (or "own key used up/rejected, shared key"), and a link to the engine's own page for the image. If Telegram rejects the rich message, or there is nothing to embed (no `PUBLIC_URL`, or a non-photo Telegram would not give), the same report goes out as plain HTML with the original media resent by file_id as a reply to it, because Telegram cannot resend thumbnails. With `REPORT_RESULTS` off, a failed search is an `error()` report instead. `key()` reports a user's own key being added (with the account summary), removed, refused at `/apikey` or rejected during a search (from `search()`): who, via which bot, never the key; it follows `REPORT_RESULTS` and never raises. `error()` reports handler failures. The bot token is replaced in every error text, and `observability.redact` removes what only its shape gives away. An admin who never started a bot makes its reports fail with Forbidden: logged as a WARNING once per bot and admin (not a Sentry event), the rest are skipped silently.
- `web.py` — the single aiohttp app: a webhook per bot (aiogram `SimpleRequestHandler` wrapped in `counted`, which counts the request in `InFlight` and answers 503 once shutdown has begun; webhook mode only, `X-Telegram-Bot-Api-Secret-Token` checked, 401 otherwise; `webhooks()`: the primary bot on `POST /` with `WEBHOOK_SECRET`, where its webhook has always been, each extra bot on `POST /<bot id>/` with its derived secret; no path holds a token), `GET /img/<bot id>/<file_id>` (through that bot, 404 for an unknown one; validates the id, `getFile` on every request, streams images only, `HEAD` without downloading, 404/502 otherwise), `GET /img/<file_id>` (the same through the primary bot, for links sent before there were several bots), `GET /healthz`.
- `outages.py` — what both engine clients share about an engine that does not answer: `RETRY_SECONDS` (3), `UNREACHABLE` (httpx timeouts, network errors, a dropped connection), `SLOW` (the timeouts that take the whole minute), `is_down` (a 5xx), `status` (`HTTP 521 (Cloudflare: web server is down)`, the names Cloudflare gives 520-524; never the body), `describe` (the httpx error's name and reason).
- `observability.py` — `init_sentry`, `is_expected`, `Scrubber`, `redact` (also used by `RedactingFormatter` and the `Reporter`), `tag_bot`; see Sentry.
- `texts.py` — user-facing strings.

## Sentry

Org `nicosmile`, project `mikke-bot`, team `telegram-bots`, US region (https://nicosmile.sentry.io/projects/mikke-bot/). `SENTRY_DSN` turns it on (blank or unset: the SDK is never initialised, so tests and local runs send nothing); `SENTRY_ENVIRONMENT` (default `production`, `development` for local runs); `SENTRY_TRACES_SAMPLE_RATE` (default 0.0, errors only). The release is `SENTRY_RELEASE`: the Dockerfile's `SENTRY_RELEASE` build arg, which CI sets to `mikke-bot@<commit sha>`; without it there is no release (the SDK's `git rev-parse HEAD` guess is switched off). After a deploy, the workflow's `getsentry/action-release` step creates that release in Sentry with its commits (`set_commits: auto`, so suspect commits work) and a `production` deploy marker; it uses the `SENTRY_AUTH_TOKEN` repo secret (an org token with the fixed `org:ci` scope, "mikke-bot GitHub Actions (releases)") and is `continue-on-error`. The org's GitHub integration is installed on the Nyasume account, so stack traces link to this repo and "Fixes MIKKE-BOT-N" in a commit resolves the issue.

- Events carry the tag `bot`, the username of the bot that received the update (`tag_bot`, an outer middleware that forks the scope) or of the `/img/` link's bot (the request's scope).
- Reported, once each: handler errors (aiogram's error handler swallows them, so `on_error`'s `logger.error` is the event, through the logging integration; there is no aiogram integration), exceptions in the aiohttp routes `/img/` and the webhook (aiohttp integration, which ignores aiohttp's own error log), and every other ERROR log, like `logger.exception` in the searchers (SauceNAO or trace.moe failing, download failures). INFO and above are breadcrumbs.
- Not reported: SauceNAO and trace.moe quotas (`QuotaExceededError`), SauceNAO or trace.moe down or out of reach after the retry (`UnavailableError`, WARNING logs; the owner report still shows it as an error, and the key check logs it the same way), a user's key SauceNAO rejects (INFO log), no result, flood protection, Telegram's "message is not modified", a message deleted before the answer, a user who blocked the bot, an admin who never started it, or a chat that took away its right to write (`is_expected`, also enforced in `before_send`), `/img/` 404 and 502 (`failed_request_status_codes=set()`). They stay INFO/WARNING logs.
- Scrubbing: `before_send`, `before_send_transaction` and `before_breadcrumb` replace `Settings.secrets()` (every bot token and webhook secret among them, also percent-encoded) and any `/bot<id>:<token>`, `api_key=` value or `/apikey` argument in every string with `[Filtered]` (users' keys are not in `Settings.secrets()`: only their shape gives them away, and nothing logs them), and, in Sentry only, the searched images: the file_id of `/img/` paths and the URL of inline searches (`url=`, `url:`), since a file_id opens the user's picture through `/img/` (the logs and the owner reports keep them; `file_unique_id`s fetch nothing and stay); the `EventScrubber` denylist adds `X-Telegram-Bot-Api-Secret-Token` and `x-trace-key`; `request.env` (REMOTE_ADDR) is dropped. No Telegram user data beyond numeric ids: `include_local_variables=False` (locals hold messages and token URLs), `max_request_body_size="never"` (webhook bodies are whole updates), `send_default_pii=False`, and `on_error` sets only the user id, the update type and the chat id. `trace_propagation_targets=[]` keeps tracing headers away from Telegram, SauceNAO and trace.moe.
- Tests (`tests/test_observability.py`) start the SDK with a recording `Transport`, so nothing leaves the machine.

## Things to watch

- The bot tokens must never leave the process: SauceNAO and trace.moe get bytes, fallback and report links use `<PUBLIC_URL>/img/<bot id>/<file_id>`, webhook paths use the bot id. aiohttp errors from Telegram file downloads quote the file URL, token included, so never log or report them raw (`DownloadError`, the `/img/` warning, the `Reporter`'s error texts, `RedactingFormatter`). httpx logging is set to WARNING because it logs request URLs, and the SauceNAO `api_key` is in the query string.
- Users' SauceNAO keys are as secret as the tokens: never logged, reported or shown (only `UserKey.masked`), never in an error text (`SauceNao._hide`, the `Searcher`, the `/apikey` check's error log), and a key sent in a group is deleted, not saved. They are stored as given, without encryption, in `DATA_DIR`; `tests/test_observability.py` and `tests/test_apikey.py` check that none reaches Sentry, the logs or the owner.
- Flood protection counts updates handled out of order right when they come in runs (a backlog after a newer update, or the reverse); old and new ones interleaved across more than a window can be undercounted. Telegram's ordered delivery does not produce that, and it was judged not worth more bookkeeping (decided in the whole-repository review).
- A search can now wait up to about a minute for its SauceNAO slot (twice that in the rare case where it waited behind a search of the same image that then failed), plus 3 s and one more request when SauceNAO is down and gets its retry. aiogram answers webhooks at once and handles each update in its own task (polling too), so a wait blocks nothing else; but the 8 s shutdown grace does not cover it, and a search still waiting at a deploy leaves its placeholder spinning.
- `/img/` calls `getFile` per request on purpose: file_ids stay valid, `file_path` links expire after about an hour, and fallback links sit in old messages. That is also why `/img/<file_id>`, without a bot id, must keep working through the primary bot.
- Inline results carry the 🔍 keyboard on purpose: without a keyboard Telegram sends no `inline_message_id` to edit. `chosen_inline_result` needs inline feedback enabled in @BotFather (`/setinlinefeedback`), for each bot.
- Group keywords (`sauce` without a slash) and favourite-group photos only reach a bot with its privacy mode off (set per bot in @BotFather).
- trace.moe never runs automatically. A guest gets 100 searches per IP (the API docs and server code count a rolling 24 hours; `GET https://api.trace.moe/me` shows quota and usage, and anything else on the server calling trace.moe uses the same quota) and concurrency 1; failed searches (4xx/5xx) do not count. Keep it behind the button, and keep the lock and the cache.
- Deliberately dropped from production: Amplitude analytics, proxy rotation, TinEye scraping, `webpToPng.php`, pm2, the storebot rating text, the TinEye `sn|` callback buttons, the `/privacy` command.

- One-time setup of the volume, before the first deploy of an image with `/apikey`: copy this repo's `docker-compose.yml` (the `volumes:` entries and `DATA_DIR: /data`) to `~/BOTS/mikke/docker-compose.yml`, then deploy as usual. `docker compose up -d` creates `mikke-data` on first use; an empty named volume starts as a copy of the image's `/data`, so it already belongs to the `bot` user (uid 10001, mode 700) and needs no chown. The server's `.env` needs no new line (and should not set `DATA_DIR`). Check with `docker exec mikke ls -l /data` after the first key is added. Backup: `docker run --rm -v mikke-data:/data -v "$PWD":/backup python:3.13-slim python -c "import sqlite3; sqlite3.connect('/data/mikke.sqlite3').backup(sqlite3.connect('/backup/mikke.sqlite3'))"`. Deployed before the compose file is updated, the bot still runs, but the keys live in the container and are lost at the next deploy.
